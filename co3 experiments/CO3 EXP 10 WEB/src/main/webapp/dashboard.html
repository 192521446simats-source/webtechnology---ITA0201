Why does this happen?

Servlet containers commonly use multiple threads to process requests. A servlet instance can therefore be accessed by multiple request threads at the same time — and any mutable field on that instance is fair game for all of them, concurrently.

Unsafe vs. thread-safe implementation

UnsafeIncrement.javaUNSAFE
private int visitorCount = 0;

int current = visitorCount;         // 1. READ
visitorCount = current + 1;        // 2. WRITE
Two threads can read the same value and overwrite each other's updates.
SafeIncrement.javaTHREAD-SAFE
private final AtomicInteger visitorCount =
        new AtomicInteger(0);

int current =
        visitorCount.incrementAndGet();  // atomic
AtomicInteger performs the increment atomically, preventing lost updates.
Scope matters

Why are local variables safer?

Not every variable in a servlet needs protecting — it depends entirely on where it lives.

SHARED

Instance variable

private int count;

Declared on the servlet class. One copy exists for the whole servlet instance, and it is shared between every request thread the container ever dispatches to that instance. Mutating it needs explicit protection.

PER-REQUEST

Local variable

protected void doGet(...) {
    int requestNumber = 10;
}

Declared inside a method. It belongs to that one method invocation and is stored on that thread's own call stack — no other thread can see or touch it. It is therefore always safe, with zero synchronization.

Local variables belong to the individual method invocation and are stored separately for each executing thread. They are therefore safer for request-specific data — the same servlet can process a thousand concurrent requests and every one of them gets its own private requestNumber.

Conclusion

Servlets are multi-threaded by nature. Shared mutable instance variables must be protected when multiple requests can access them concurrently. AtomicInteger provides a simple and efficient solution for counters. Local variables are safer for request-specific data because each request has its own method invocation.
